This one goes into the AI substrate / context architecture bucket.

Core concept captured: context window is simplicity, RAG is infrastructure/control. The real question is not “RAG or long context?” It is which context-injection mode should OMNI use for each workflow. The transcript frames LLMs as frozen in time and lacking private/internal data, so the core architecture problem is getting the right data into the model at the right time.

OMNI-relevant gems:

Long context is good for bounded global reasoning
Full contract review, comparing two documents, “what’s missing between doc A and doc B,” whole-case analysis, etc.
RAG is still needed for enterprise/longitudinal scale
OMNI has infinite-ish data: patients, messages, labs, observations, documents, operators, policies, tasks, commerce, history. That cannot just be pasted into every prompt.
Silent retrieval failure is a real architecture risk
If retrieval misses the key source, the model never sees it. OMNI will need evals for retrieval quality, not just answer quality.
Needle-in-haystack is also a real architecture risk
If we dump too much context, the model may miss or dilute the important piece. So bigger context is not automatically safer.
OMNI needs a context strategy router
Not “always RAG” or “always long context.” More like:
bounded full-context packet
retrieval packet
longitudinal patient packet
source-grounded evidence packet
global comparison packet
no-AI / deterministic-only mode

This reinforces the Stanford point: context architecture is a first-class OMNI substrate, not a prompt detail.>
