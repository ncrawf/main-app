## 2. ChatGPT distillation

<Ingested into the active thread. This one is very important because it gives us a clean architectural separation we were missing.

Core OMNI takeaway:

MCP is connectivity. ADK is orchestration. OMNI needs both concepts, but vendor-neutralized into our own architecture.

The transcript frames the split clearly: MCP answers, “How does my agent talk to external tools/data?” while ADK answers, “How do I build, structure, run, and orchestrate the agent or team of agents?”

For OMNI, I would translate it like this:

1. MCP-like layer = Tool / Context Access Plane

This is where OMNI agents access the world:

databases
files
APIs
partner systems
internal services
MCP servers
clinical knowledge bases
scheduling, commerce, D7, D5, CNS, etc.
repo/build tools for agents working on OMNI

MCP primitives matter: tools, resources, prompts. Tools are callable actions, resources are readable context, prompts are reusable templates. That maps almost directly to OMNI’s future AI capability registry.

2. ADK-like layer = Agent Runtime / Orchestration Plane

This is where OMNI defines agent behavior:

agent identity
model
instructions
allowed tools
memory/state
events
runners
controlled reasoning loop
deterministic vs LLM-driven workflow
sequential / parallel / loop agents
multi-agent delegation

The biggest gem is the runner pattern: the agent yields a tool call or state change, then the runner handles consequences before the agent continues. That is exactly the kind of control OMNI needs for clinical/business safety.

3. The phrase we need to preserve

ADK defines what the agent should do; MCP defines how it communicates with the world.

That is a thesis-level sentence. The transcript basically says this directly near the end: ADK structures agent cognition, planning, tool orchestration, retries, guardrails; MCP standardizes external tool/data access.

OMNI routing

Thesis:
AI substrate should include separate planes for context/tool access and agent orchestration.

System map:
Add or sharpen:

AI Runtime / Agent Orchestration Plane
Tool/Context Access Plane
AI Capability Registry
Agent session state / memory
Runner / execution controller
Agent-to-agent delegation boundary

Contracts:
Each domain should declare:

what resources agents may read
what tools agents may call
what actions agents may propose
what actions they may commit, if any
what must be routed through deterministic policy or human approval

Build OS:
This is huge for agents building OMNI. Cursor/Opus should not be “one giant coding agent with repo access.” It should be closer to:

root orchestrator
planner
implementer
reviewer
test runner
documentation/checkpoint agent
contract validator
migration/schema validator

With tool access controlled through MCP-like or CLI-like pathways, not ad hoc free-for-all.

Best keeper line:

OMNI should not treat agents as prompts with tools. OMNI should treat agents as governed execution units running inside a controlled orchestration plane, with standardized access to tools, resources, prompts, state, memory, traces, and approval gates.>
