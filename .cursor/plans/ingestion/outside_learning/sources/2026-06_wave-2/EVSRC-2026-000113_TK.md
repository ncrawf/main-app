Core takeaway

The keeper is:

Agent traces are becoming their own data infrastructure problem.

That matters for OMNI because once agents are doing real work, their traces will not be cute little logs.

They will include:

inputs,
context packets,
model calls,
tool calls,
subagent steps,
file changes,
code execution,
human approvals,
messages drafted,
actions proposed,
domain commits,
errors,
forks,
replays,
costs,
latencies,
screenshots,
voice/image/media,
and evidence links.

Traditional app logs may not be enough.

The big OMNI translation

Agent traces are behavioral records.

This source reinforces the ADLC keynote point: a trace is not merely debugging output. It is the behavioral record of what the agent actually did.

OMNI translation:

Agent traces may become evidence for:

why an action was proposed,
what context was used,
what tool was called,
what the agent omitted,
what human approved,
what failed,
what changed,
and what should be improved.

Keeper:

A trace is the behavioral record of an agent under authority.

Observability becomes data architecture.

SmithDB’s existence says agent observability is not just dashboards.

It is a storage/query/retrieval problem:

large payloads,
nested steps,
long sessions,
multimodal traces,
high volume,
trace search,
trace filtering,
fast random access,
data residency,
cost control.

OMNI should not assume generic logging solves agent oversight.

Keeper:

Agent observability is a data platform, not a log viewer.

Trace infrastructure may become D7-adjacent.

OMNI should be careful here.

Not every trace is a D7 artifact.
Not every trace should be permanent evidence.
Not every trace should be visible to every user.
Not every trace belongs in clinical record.

But some traces will matter legally, operationally, clinically, or architecturally.

OMNI needs trace classification:

debug trace,
eval trace,
audit trace,
clinical-support trace,
patient-communication trace,
security trace,
incident trace,
domain-commit trace,
source-ingestion trace,
Build OS trace.

Keeper:

Some traces are disposable telemetry. Some traces are evidence. Classify them.

Trace query patterns are agent-native.

Traditional observability asks:

what service failed,
what latency spiked,
what error happened?

Agent observability asks:

what did the agent think it was doing,
what context did it see,
which tool path did it choose,
where did it drift,
which subagent failed,
which approval was skipped,
which evidence was missing,
which similar traces exist,
what pattern is repeating?

OMNI needs this kind of query posture.

Keeper:

Agent traces need semantic and behavioral queries, not only error queries.

Existence of SmithDB supports the Build OS trace layer.

This source strengthens the argument that OMNI Build OS should not treat traces as afterthoughts.

Build OS needs a trace layer that can support:

agent debugging,
eval creation,
pattern clustering,
regression detection,
source-run replay,
contract-extraction audit,
code-agent review,
workflow goodput analysis,
and background improvement agents.

Keeper:

If Build OS has agents, Build OS needs trace infrastructure.

Do not overreact and build SmithDB tomorrow.

This is the caution.

OMNI does not need to build its own purpose-built trace database Day 0.

Early path could be:

use vendor observability,
store structured traces in existing DB/object storage,
export trace bundles,
keep D7/audit-critical trace records separately,
trial LangSmith for internal Build OS,
learn actual access patterns,
