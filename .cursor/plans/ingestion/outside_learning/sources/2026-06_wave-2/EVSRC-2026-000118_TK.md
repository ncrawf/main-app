Core takeaway
The keeper is:
Agent observability and agent evaluation are tightly coupled because agent behavior emerges at runtime.
In traditional software, the code is usually the source of truth. If something breaks, you inspect the code path, stack trace, logs, and function behavior.
With agents, the meaningful logic often lives in:
the prompt,
the tools,
the context,
the conversation thread,
the intermediate reasoning,
the tool-call trajectory,
and the model’s runtime choices.
So the only way to know what happened is to inspect the run, trace, and thread.
The big OMNI translation
You do not know what an agent will do until users use it.
This is the biggest conceptual point.
Software has constrained inputs. Agents have natural-language inputs, open-ended user behavior, non-deterministic model behavior, and tool/action loops.
OMNI translation:
You cannot fully pre-specify every provider, staff, patient, source-ingestion, or Build OS agent path before launch.
You need:
offline evals before launch,
online evals after launch,
trace review,
ad hoc investigation,
human feedback,
and production-derived regression cases.
Keeper:
Agent reliability is discovered and improved in production, not proven once before launch.
Code is no longer the full source of truth.
The source says that in agentic systems, code may only show prompt and tools. It does not tell you what the agent actually did.
OMNI translation:
For OMNI agents, the behavioral truth is not just in code.
It is in:
what context packet was assembled,
what evidence was included or omitted,
what tool was selected,
what model was used,
what human said earlier,
what domain state existed,
what action was proposed,
what approval was requested,
what trace was produced.
Keeper:
Agent behavior lives in the trace.
Runs, traces, and threads are a useful primitive ladder.
LangChain defines:
run = one execution step, often one LLM call;
trace = ordered collection of runs for a full execution;
thread = grouped multi-turn interaction over time.
This is very useful for OMNI.
OMNI should probably preserve this conceptual ladder, even if names change.
Run-level:
did this LLM call choose the right tool or output?
Trace-level:
did the whole agent trajectory complete the task correctly?
Thread-level:
did the agent preserve context and behave well across multiple turns?
Keeper:
Evaluate the step, the trajectory, and the conversation.
Debugging means inspecting context at each LLM call.
The source emphasizes that agent mistakes often happen during LLM calls, so you need to understand the context at each call.
This is directly OMNI.

What not to import blindly
Do not treat LangSmith terminology as automatically OMNI terminology.
Do not assume “track everything” is acceptable in PHI-heavy or operator-sensitive workflows.
Do not let traces become clinical evidence without D7/domain rules.
Do not assume online evals prove correctness when no ground truth exists.
Do not let production-derived evals leak patient/operator data.
Do not over-index on trace dashboards without improvement routing.
Do not pretend agent evals are solved because traces exist.

For production agents, traces are not optional logs. They are the behavioral record that powers debugging, evaluation, regression prevention, and improvement.
