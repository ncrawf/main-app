Core takeaway

The keeper is:

A useful agent-builder product should let people move from one-off work to reusable workflow.

That matters for OMNI because many future agents will probably begin as ad hoc work:

“analyze this source,”
“draft this follow-up,”
“check this patient packet,”
“review this policy,”
“pull this report,”
“summarize these traces,”
“run this daily scan.”

If the work repeats, the system should help promote it into a governed reusable agent, skill, schedule, or workflow.

The big OMNI translation

One-off agent chat is the front door.

The demo starts with an always-available agent that can use tools like Google Calendar or email.

OMNI translation:

A general agent chat can be useful as an exploratory work surface, especially for low-risk internal tasks.

But in OMNI, the chat should not be the authority layer.

The agent may help draft, fetch, prepare, summarize, classify, or propose.

It should not silently commit clinical, commerce, scheduling, identity, D7, or external communication truth without domain authority and approval.

Keeper:

Ad hoc agent chat is a work surface, not a commit layer.

Conversation-to-agent promotion is the real pattern.

The demo shows turning a conversation into a dedicated reusable agent with one click.

This is a good idea.

OMNI version:

If Nick or a staff member repeatedly asks for the same task, the system should notice:

this should become a skill,
this should become a scheduled scan,
this should become a workflow,
this should become an eval,
this should become a provider packet section,
this should become a source-ingestion routine,
this should become an ops report.

But promotion must be governed.

Keeper:

Repeated work should become reusable capability.

Reusable agents need trigger semantics.

The demo supports manual triggers, schedules, Slack/email external events.

That maps directly to OMNI.

OMNI agent triggers may include:

daily morning ops scan,
new patient intake submitted,
lab result received,
photo uploaded,
message unanswered,
payment failed,
appointment completed,
service occurrence completed,
source transcript dropped,
trace failure cluster detected,
staff task overdue,
lead not contacted,
membership renewal risk.

Keeper:

The trigger is part of the agent definition.

File uploads as context are useful but not enough.

The demo lets users upload CSVs, text files, or images for the agent to use as context.

Useful.

OMNI will need file/context ingestion constantly:

source transcripts,
screenshots,
labs,
PDFs,
patient photos,
CSV exports,
contracts,
policies,
reports,
staff notes,
trace bundles.

But file upload is not the same as evidence custody.

OMNI version needs:

D7 artifact handling,
source provenance,
authority label,
visibility scope,
PHI/purpose-of-use boundary,
retention,
extraction,
review,
and promotion rules.

Keeper:

Files can feed context. D7/evidence rules decide what they become.

Tool registry is a serious primitive.

The demo’s centralized tool page is more important than it looks.

Agents need authenticated tools, and tool sprawl gets dangerous fast.

OMNI needs a tool/capability registry that knows:

tool name,
owner,
scope,
credential posture,

allowed actions,

and whether the tool may touch PHI or production systems.

Keeper:

No tool should be “just connected.” Every tool is a capability boundary.

MCP is useful and dangerous.

The demo casually supports third-party MCP servers.

That is directionally right, but OMNI must be stricter.

A third-party MCP server can become:

data exfiltration path,
prompt-injection source,
credential exposure,
shadow authority,
policy bypass,
or vendor lock-in surface.

OMNI §C needs tool admission and quarantine rules before external capability servers become common.

Keeper:

MCP is not magic plumbing. It is external capability access.

Agent Builder is a UX benchmark, not a core constitution.

Should OMNI use this product?

Maybe for low-risk prototyping or internal Build OS experiments.

But not as the core OMNI care/business agent builder.

Generic agent builders are too loose for OMNI’s authority model unless wrapped heavily.

OMNI needs:

human approval gates,
trace/eval governance,

and rollback.

Keeper:

Use generic builder UX as inspiration. Own the governed builder semantics.

Domain experts building agents is powerful but risky.

This source reinforces a recurring theme from LangChain Fleet, Benchling, Uber, and Cisco CX:

people closest to the work should help shape agents.

But OMNI must prevent shadow workflows.

A staff member should maybe create:

a draft helper,

Keeper:

Domain experts can shape agents; governance decides what agents may do.

Keeper doctrine

Repeated ad hoc agent work should be promotable into reusable capability, but promotion must be governed.

Second:

Every reusable agent needs trigger semantics, tool scope, context policy, authority boundary, trace policy, and owner.

Third:

A centralized tool registry is required before agents can safely use workspace tools and third-party MCP servers.

Fourth:

Uploaded files may provide context, but evidence/custody/truth status must be handled by OMNI’s D7/Knowledge Reservoir rules.

Fifth:

Agent-builder UX should empower domain experts without letting them create shadow truth or unsafe automations.

What not to import blindly

Do not use generic Agent Builder as OMNI’s core care agent system without heavy wrapping.

Do not let one-click conversation-to-agent promotion bypass review.

Do not let scheduled agents send messages or mutate domain state without authority gates.

Do not treat uploaded files as trusted evidence automatically.

Do not let users authenticate arbitrary MCP servers into sensitive OMNI contexts.

Do not expose broad workspace tools to agents without least-privilege scopes.

Do not let convenience become shadow automation.

Do-not-miss lesson

This source gives OMNI a product UX law:

The system should make it easy to turn repeated work into reusable agents, but the promotion path must add governance: owner, trigger, tools, context, authority, approval, trace, eval, and rollback.

Shortest OMNI version:

Ad hoc chat is the starting point. Reusable agent is the promoted form. Trigger defines when it runs. Tool registry defines what it can touch. Governance defines what it may actually do.
