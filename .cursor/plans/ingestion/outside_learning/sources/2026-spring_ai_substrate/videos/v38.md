LLMs are stochastic machines and thus fundamentally unpredictable. If you will use them in any context where they initiate action then, necessarily, they entail some security risk that they may use that action improperly. But exactly the same risk exists when en employee is charged with an action. The questions to answer are: 1) Which kind of agent is riskier (human or machine) and why? Incidentally not all hurtful errors originate with a malicious attacker, human error may cause more harm (in the context of agentic systems bad designs may be the origin of the hurtful error). 2) What can we do to measurably decrease the machine agent risk? Using dynamic time-bound narrow credentials may be a partial answer (it certainly cannot hurt). Using many independent weak agents, instead of a few powerful ones, may be a partial answer (and do for better design). Using a council of agents to agree on some action may be a partial (though inefficient) answer, with the bonus of raising alarms that may reveal vulnerabilities when strange disagreements occur.  A similar idea (used, I understand, in nuclear power plants) would be to use completely independent systems and only act when they agree. - As for CIBA, I think that putting a human in the loop does not significantly decrease the risk of an hurtful error, but only decreases the legal risk: Most users won't even understand what they are being asked and will tend to approve everything. A better solution in that way would be a hybrid system: An independent and untouchable AI that knows the user's interests deciding whether to approve an agent's action or not, and only when in doubt explicitly asking the user for permission after explaining them exactly why they are being asked. In turn such exchanges could be used to improve the AI.

## 2. ChatGPT distillation

<Ingested. This one is very important because it gives us the runtime-security version of the same principle we’ve been circling:

Agents should not have standing privilege. They should receive dynamic, session-bound, intent-bound authority at action time.

The key concept is agentic runtime security for non-human identity. Instead of hardcoding static database keys, LLM provider keys, SaaS credentials, or broad service-account access, the agent should request narrowly scoped credentials only when it needs to act, and those credentials should expire or be revoked automatically.

OMNI translation

This strengthens the need for an Agent Runtime Security Plane or Non-Human Identity Plane inside the broader AI substrate.

For OMNI, this means an AI agent should not simply “have access” to:

patient records
clinical notes
labs
messaging
scheduling
prescriptions
payments
internal tools
external APIs
MCP servers
other agents

Instead, it should receive a task-scoped grant like:

“For this authenticated actor, in this session, for this purpose, allow this agent to read these specific records and propose this action, but require separate approval before committing.”

The keeper primitives

This one adds several primitives we should preserve:

1. Dynamic credentials
Just-in-time credentials generated per session/action, time-bounded, automatically revoked.

2. Intent-bound access
The agent should request access based on the specific action it is trying to perform, not from a permanent permission bucket.

3. Non-human identity
Agents, workloads, services, and MCP connectors need their own governed identity. They should not just impersonate a human forever.

4. User identity layering
The user identity still matters, but it should be combined with agent identity, session, purpose, and action context.

5. Sensitive-action escalation
For high-impact actions, use an out-of-band approval pattern like OAuth 2.0 CIBA: the agent determines the desired sensitive action, then the identity provider asks the user to approve the specific action outside the current browser/agent context.

6. Prompt-injection containment
If a malicious instruction says “offboard all employees” or, in OMNI terms, “message every patient,” “cancel all appointments,” “release PHI,” or “change this medication,” the agent still should not possess enough static authority to do it silently.

Important caveat

CIBA-style approval is useful, but it cannot become “click OK 900 times.” That becomes approval fatigue and just moves the failure to the human. For OMNI, this means approvals need risk-tiering:

low-risk read/propose actions: auto-authorized within envelope
medium-risk draft/queue actions: human review in workflow
high-risk irreversible or clinical/financial actions: explicit out-of-band or privileged confirmation
forbidden actions: no credential issued at all
OMNI doctrine candidate

OMNI agents must not operate with ambient authority. Every agent action must be mediated through scoped, session-bound, intent-bound, revocable authorization.

And the sharper version:

Agent access is not a role; it is a grant.

This belongs directly in the AI substrate pass, but it also reinforces Federation, RBAC, CNS, Messaging, D7, and the Build OS. It gives us the runtime enforcement layer behind the words “authority,” “consent,” “purpose,” and “agent action.”>
