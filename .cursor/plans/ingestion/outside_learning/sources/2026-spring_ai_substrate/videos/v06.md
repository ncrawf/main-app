@NarekSaaryan4 weeks ago10:50

I don’t think the real advantage here is MCP itself.

The reason the model didn’t have to reverse-engineer the JavaScript-heavy website in the MCP setup is that this reverse-engineering work had already been done once and encoded into the MCP server. Without that, the agent had to spend tokens rediscovering the same procedure from scratch.

But MCP is not the only way to persist that kind of procedural knowledge. Anthropic’s Skills specification gives you a similar pattern: you can package instructions together with supporting files and executable scripts. For example, you could write a script that knows how to use a headless browser to fetch or inspect the MCP docs, then bundle that script with a Skill that tells the agent when and how to use it.

That also gives you a context-management advantage: the agent only loads the relevant Skill when the task calls for it, rather than receiving every available tool description in the startup context, which is closer to how MCP tools are typically exposed.

￼@PythonDanny4 days agoGreat breakdown! The 55k token point for the GitHub MCP server is real and worth taking seriously — but there's a crucial nuance worth adding: the problem isn't MCP itself, it's loading every single tool at once regardless of need.

Most frontend clients actually let you cherry-pick individual tools or categories from a connected MCP server per chat, so you're not forced to load all 80 tools when you only need 2. The token bloat issue is much more of an implementation and API-level concern, where the developer or client has to manually curate which tools go into the tools parameter.

So the real design question for MCP is: should tool discovery be lazy (load schemas dynamically on demand) rather than eager (dump everything upfront)? Newer MCP client and server implementations are already moving in this direction, which completely defuses the "bloat" argument.

That said, the web fetcher example was the strongest argument in the video — that's exactly the sweet spot for MCP: when the gap between raw CLI and the actual desired output is too large for the agent to reliably bridge on its own. Nicely demonstrated!

## 2. ChatGPT distillation

<Ingested.

This one belongs in the Tool Access / MCP / Build OS execution layer bucket.

Core distinction:

CLI and MCP are both ways agents interact with the world, but they are good at different jobs. CLI is compact and powerful when the command maps directly to the task. MCP is better when the raw tool is too low-level, authenticated, vendor-specific, browser/rendering-dependent, or needs governance/audit/access-control around it.

The OMNI-relevant takeaways:

1. MCP is not automatically better.
If an agent needs to run git status, search files, inspect logs, or perform simple local dev operations, CLI may be cheaper, faster, and less context-heavy.

2. MCP wins when abstraction/governance matters.
For OMNI runtime, this is huge. Clinical, messaging, patient, commerce, scheduling, and federation capabilities should not be random CLI/API calls. They need structured capability schemas, auth, audit, per-user access control, and consistent outputs.

3. Tool exposure itself is a context problem.
The GitHub MCP example with many tools bloating the context window is a warning. OMNI should not dump every tool/capability into every agent context. We need lazy tool discovery / scoped tool visibility / capability loading by lane or task.

4. “Right tool for the right job” becomes Build OS doctrine.
For AI on OMNI:

CLI is useful for repo-local work, file ops, grep, tests, migrations, logs, git inspection.
MCP/capability tools are useful when actions need structured auth, vendor abstraction, browser rendering, external systems, audit, or policy enforcement.

For AI within OMNI:

Prefer governed capabilities/MCP-style interfaces, not raw vendor APIs.
Agents should say what they want done through an authorized capability.
The system handles auth, policy, audit, and adapter specifics.

5. This reinforces a dual tool model.
OMNI probably needs both:

Build tools: CLI, scripts, tests, repo search, migrations.
Runtime capabilities: MCP/capability registry, domain actions, context access, messaging, scheduling, entitlement, observations, D7 materialization.

The phrase I’d preserve:

CLI for direct local execution. MCP/capabilities for governed abstraction. Skills tell agents when and how to use either.
