<Ingested.

This one reinforces the MCP / API / capability-plane bucket.

Core distinction:

APIs are general-purpose interfaces for developers/systems.
MCP is purpose-built as an AI-agent interface layer over tools, resources, and prompt templates.

Important OMNI concepts:

1. MCP is like USB-C for AI applications.
It standardizes how AI apps/agents connect to external data sources and tools, instead of every agent learning every unique API.

2. MCP has three primitives: tools, resources, prompts.
This maps extremely well to OMNI:

Tools = actions/capabilities the agent can invoke.
Resources = read-only context/data/artifacts the agent can retrieve.
Prompts = governed templates for interacting with tools/resources/workflows.

3. Dynamic discovery is the key differentiator.
Unlike static APIs, an MCP server can tell an agent at runtime: “Here is what I can do.” This matters for OMNI because agent capability visibility should be dynamic, scoped, permissioned, and versioned — not hardcoded forever.

4. MCP and APIs are not enemies; they are layers.
MCP often wraps APIs. So for OMNI, the pattern is not “replace APIs.” It is:

Domain/vendor APIs live underneath. MCP-style capability servers expose AI-friendly, governed interfaces above them.

5. Build once, integrate many.
This is the 1BN-company relevance. OMNI should not have one-off agent integrations for every vendor/operator/tool. It needs a capability abstraction layer where the same AI workflow can work across different underlying services.

6. The key OMNI object may be a capability_server.
Potential primitives:

capability_server
capability_tool
capability_resource
capability_prompt
capability_schema
capability_visibility_policy
capability_version
capability_call
capability_result
capability_trace

The phrase I’d preserve:

MCP is an AI-facing capability interface; APIs are often the implementation underneath.

This is going to be central when we design OMNI’s AI substrate and Build OS tool/capability layer.>
