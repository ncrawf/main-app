Core concept:

Vector databases bridge the semantic gap. Traditional databases can store files, metadata, and tags, but they do not naturally represent meaning. Vector embeddings convert text, images, audio, and other unstructured data into high-dimensional numerical representations so semantically similar items can be retrieved by similarity, not just keyword match.

OMNI-relevant points:

1. Vector DBs are retrieval indexes, not truth stores.
For OMNI, the vector index should never become canonical truth. It should point back to authoritative sources: D7 artifacts, Observation records, Clinical Memory assertions, messages, policies, domain objects, etc.

2. Every embedding needs lineage.
Each vector should know: source object, source version, timestamp, tenant/operator, visibility grant, consent state, authority level, freshness, and invalidation rules.

3. Multimodal embeddings matter.
Text, images, audio, documents, and eventually video/device data may use different embedding models. This matters for clinical photos, before/after media, lab reports, intake text, patient messages, call transcripts, and documents.

4. Approximate search is a tradeoff.
ANN indexes like HNSW/IVF trade a small amount of accuracy for speed. That means retrieval quality needs evals. In OMNI, missing the right source can become a safety problem.

5. Semantic similarity is not authority.
A chunk being “close” to a query does not mean it is true, current, clinically adopted, or visible to this user. Retrieval must pass through Federation/RBAC/consent/policy/context gates.

Phrase to preserve:

OMNI’s vector layer is a semantic access path over governed truth, not a second memory of truth.e>
