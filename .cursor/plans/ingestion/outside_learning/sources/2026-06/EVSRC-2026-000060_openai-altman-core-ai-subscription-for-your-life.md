This one is strategically huge and a little scary — but in a clarifying way.

It tells us what not to make OMNI.

OpenAI’s ambition here is basically:

Be the core personal AI subscription / memory layer / model layer / OS-like AI interface for a person’s life.

Sam describes ChatGPT evolving into a deeply personal AI service that remembers broad life context, works across services, and eventually has platform/API/SDK/protocol-like surfaces for other apps to plug into. He even sketches a future where OpenAI sign-in/context can follow users into other services, with authentication, payment, tools, and data transfer built into a new internet-level protocol.

So the OMNI lesson is sharp:

Do not compete with OpenAI as the generic personal AI. Build the governed care/business operating layer that a generic personal AI must interface with.

Core takeaway

OpenAI wants to own the general intelligence relationship:

the user’s core AI subscription,
long-lived memory/context,
voice/device surfaces,
smarter models,
coding/action capabilities,
platform/API/SDK layer,
eventually protocol-level agent interaction.

That means OMNI should assume a world where patients, providers, employees, vendors, and maybe even businesses already have powerful generic AI agents.

OMNI should not fight that. OMNI should be the system that answers:

What is this agent allowed to know?
What can it request?
What is patient-source vs clinically adopted?
What needs provider review?
What is official Bloom/OMNI truth?
What can be written back?
What gets documented?
What becomes care action?

OMNI translation
1. This validates §C hard.

Sam’s “new protocol on the level of HTTP” line is probably the most §C-relevant thing in the transcript. He describes a future where agents expose/use tools and where authentication, payment, and data transfer are built into the protocol layer.

That is basically the external-world version of OMNI’s Governed Capability Exchange.

OMNI needs to be ready for:

ChatGPT-like user agents,
patient-delegated agents,
provider agents,
vendor agents,
insurance agents,
pharmacy/lab agents,
internal OMNI agents,
external consumer AI subscriptions.

The doctrine:

OMNI must expose governed capabilities, not raw system access.

External agents should not “browse the clinic.” They should request scoped capabilities:

check eligibility,
request appointment options,
submit patient-provided info,
retrieve approved aftercare instructions,
ask for refill readiness state,
request a provider-reviewed summary,
transmit records under consent.
2. OpenAI may own generic memory; OMNI must own domain authority.

Sam’s platonic ideal is a tiny reasoning model with a trillion-token context containing your whole life: conversations, emails, books, data sources, and company data appended over time.

That is powerful — and dangerous for healthcare if treated as authority.

A patient’s personal AI may know everything the patient has ever said. But it still does not own:

clinical adoption,
provider judgment,
prescription authority,
consent enforcement,
documentation truth,
care commitments,
billing/entitlement truth,
scheduling truth,
regulatory state.

So OMNI’s position should be:

Personal AI may carry context. OMNI carries care authority.

That line matters.

3. “Core AI subscription” is a threat only if OMNI is just an assistant.

If OMNI is “the AI assistant for patients,” OpenAI can crush it.

If OMNI is “the AI chat layer for clinics,” OpenAI can crush it.

If OMNI is “a better memory app for care,” OpenAI can crush it.

But if OMNI is the governed operating system across care/business truth — identity, consent, scheduling, occurrence, commerce, documents, observation, clinical memory, CNS, messaging, workforce, audit, domain commits — then OpenAI becomes a model/provider/interface layer OMNI can use or interface with.

That is the strategic distinction:

Do not build where foundation labs are structurally incentivized to go. Build where domain authority, workflow truth, compliance, and operational commit live.

4. Coding as actuation reinforces OMNI’s tool/capability model.

Sam says coding is central because models need to make things happen in the world: produce programs, call APIs, and actuate services.

For OMNI, that means code/tool use is not just a developer thing. It is how agents act.

But in care, code/tool actuation must be governed:

model can draft tool call,
policy checks authority,
capability envelope constrains action,
owning domain validates state,
audit records the action,
human review gates high-risk steps.

OMNI doctrine:

Actuation is capability-mediated, not model-owned.

5. Voice + GUI is a product-surface clue.

Sam says voice is extremely important and points toward voice plus GUI interaction as something not yet cracked.

That fits OMNI perfectly.

Care workflows often need both:

voice for natural human expression,
GUI for confirmation, review, context, consent, and structured state.

A patient might say: “I’m nauseous and I missed my dose.”
The UI should show: medication, timing, risk flags, prior side effects, action options, escalation.

A provider might ask: “What changed since last month?”
The UI should show: labs, meds, messages, adherence, unresolved tasks, documentation links.

Doctrine:

Voice captures intent; UI confirms state; substrate governs action.

6. Sensor data and physical-world data strengthen the Observation layer.

Sam says models are already being fed sensor data through APIs and that newer models handle this better.

OMNI already had this instinct around wearables, labs, patient-reported data, and future telemetry.

The reinforcement:

More signal is coming. The scarce thing is not ingestion; it is verification, interpretation, authority, and action usefulness.

Sensor data does not become clinical truth just because a model can read it.

7. Big-company failure mode reinforces Build OS urgency.

Sam’s answer about large companies being stuck in their ways is directly relevant. He describes AI-native adoption being blocked by slow councils, old governance rhythms, and inability to adjust every quarter or two.

OMNI cannot build like a legacy healthcare IT company.

But it also cannot be reckless.

So the line is:

Move startup-fast at the build layer, but care-grade at the commit layer.

Fast exploration, fast prototypes, fast agents, fast Build OS.

Slow/gated when touching:

clinical truth,
patient safety,
consent,
payments,
identity,
documentation,
prescriptions,
regulated actions.
8. “Working forwards” is a useful counterweight to over-planning.

Sam says he does not believe in giant backward-planned master strategies; OpenAI works forward from the things directly in front of them while staying nimble.

This matters because OMNI can over-architect.

The corrected OMNI version:

Hold the constitutional architecture, but work forward through proof-bearing wedges.

Do not plan every future robot/BCI/agent scenario before building. Define the invariants, then build the first wedge that proves them.
