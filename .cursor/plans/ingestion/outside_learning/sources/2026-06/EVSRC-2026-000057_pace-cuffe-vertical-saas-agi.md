This one is extremely high-signal for OMNI — maybe one of the most directly relevant to the actual company architecture.

Serval was “AI-native internal service management.”
Pace is AI-native process outsourcing for regulated, mission-critical back-office work.

That is much closer to OMNI than it may look at first, because OMNI is not just “software for care.” OMNI is trying to absorb fragmented operational work across care, documentation, messaging, scheduling, payments, follow-up, clinical review, and business ops — much of which today behaves like messy human BPO work.

Core takeaway

Pace’s thesis is:

AI does not merely automate isolated tasks. It can take over entire codified operational processes when the process has SOPs, measurable outputs, QA, repeatable inputs, and enough trust-building deployment work.

Jamie Cuff is explicitly arguing against stuffing AI into tiny workflow nodes. His point is that many BPO workflows existed because they were too judgment-heavy and edge-case-heavy to codify deterministically. The AI-native move is to let agents run the process end-to-end against an “agent operating procedure,” using tools, documents, reasoning, writebacks, and QA.

That is a big OMNI concept.

OMNI translation
1. This validates OMNI as an “agentic care/process operator,” not just software.

Pace is replacing BPO labor in insurance. OMNI’s parallel is not insurance BPO exactly, but the same class of work exists everywhere in healthcare:

intake review,
lab chasing,
prior auth-like workflows,
referral coordination,
refill readiness,
async follow-up,
post-procedure monitoring,
missing-document collection,
eligibility/entitlement checks,
patient message triage,
documentation assembly,
claims/billing/admin workflows,
provider queue preparation.

These are not always clean CRUD workflows. They are messy, semi-codified, judgment-heavy processes. That is precisely where deterministic SaaS struggled and where agentic systems may matter.

Doctrine line:

OMNI should identify care/business workflows that already behave like outsourced process work: high-volume, SOP-shaped, QA-able, measurable, and painful.

That may be one of the best wedge-selection filters we have.

2. “SOP → Agent Operating Procedure” is a keeper.

Pace takes customer SOPs and turns them into agent operating procedures: natural-language process instructions plus tools that allow the agent to run the workflow end-to-end.

OMNI needs this concept.

A care pathway, aftercare protocol, lab-review workflow, refill workflow, onboarding flow, or front-desk process should not only be a static document. It should be convertible into an executable, governed, testable AOP:

steps,
allowed tools,
authority gates,
required inputs,
escalation points,
expected outputs,
QA criteria,
domain writebacks,
stop conditions,
human review triggers.

Possible OMNI primitive:

care_operating_procedure or agent_operating_procedure.

But with care-grade boundaries:

AOPs do not replace domain truth. They instruct agents how to move through governed work.

3. The BPO interface is a brilliant wedge analogy.

Pace starts where workflows are already outsourced because those workflows tend to have:

existing SOPs,
defined input/output,
baseline cost,
QA process,
measurable accuracy,
change-management path,
existing operational pain.

That is a very useful OMNI wedge filter.

For OMNI, don’t start with the most abstract “AI care OS” problem. Start where there is already a recognizable operational interface:

“someone manually reviews these intakes,”
“someone manually checks these labs,”
“someone manually chases this missing info,”
“someone manually sends these follow-ups,”
“someone manually reconciles schedule/commerce/documentation,”
“someone manually converts provider judgment into patient communication.”

If a workflow already has a human doing repeatable judgment work, OMNI can model it, evaluate it, assist it, then gradually automate bounded portions.

4. “No human in the loop” should not be imported blindly — but the accuracy ladder matters.

Pace says many workflows run end-to-end without human-in-the-loop after onboarding, but they use human labeling/onboarding and self-improvement to climb from around 90% to customer-required levels like 99.5%+.

OMNI should not copy the “no human in loop” posture for clinical workflows. But it should copy the accuracy ladder:

collect examples,
label edge cases,
build eval set,
run agent,
compare expected output,
identify failure modes,
improve procedure/tooling/model,
reduce human review only where measured and safe.

Clinical OMNI version:

Human review is not a permanent crutch or a thing to remove blindly. It is a governed training/evaluation layer that can shrink only by workflow, risk class, and proof.

5. “Close the distance” maps directly to OMNI deployment.

Pace attributes successful AI deployments to forward-deployed engineering: going onsite, understanding the customer’s actual process, cleaning eval sets, integrating systems, and doing the hard work to get to production.

For OMNI, this is a huge warning against building from architecture alone.

OMNI needs deep architecture, yes. But the build has to close distance with real workflows:

Bloom front desk,
providers,
medical directors,
patients,
estheticians,
async care reviewers,
billing/commerce,
lab workflows,
partner clinics.

The right pattern is not “build substrate in a cave.” It is:

Architect deeply, then deploy close enough to reality that the architecture gets punished by workflow truth.

6. “Be the rock” is the trust posture for regulated industries.

Pace works in insurance, where trust is central. Their value “be the rock” means customers depend on them for mission-critical work.

OMNI’s version is even stronger.

In care, OMNI cannot be a clever system that sometimes works. It has to be reliable in the boring moments:

patient is scared,
provider is busy,
lab is abnormal,
med refill is blocked,
appointment was changed,
consent is missing,
documentation matters,
staff member leaves,
patient asks twice.

Doctrine line:

OMNI must be impressive less often and dependable more often.

That is the regulated-industry posture.

7. End-to-end process ownership beats node-level AI.

This is one of the biggest architecture tensions.

Pace argues that putting AI into small deterministic boxes misses the point when the real work requires judgment across the whole process.

For OMNI, this should sharpen the CNS/AOP distinction.

We do not want a fragile flowchart where each node asks an LLM to classify something with no awareness of the before/after. But we also do not want an unbounded model doing everything.

The OMNI answer:

Let agents reason across the process, but force actions through explicit tools, gates, evidence, and domain commits.

So not tiny AI nodes.
Not god-agent autonomy.
A governed end-to-end agent with substrate checkpoints.

8. “Define success criteria upfront” is Build OS gold.

Pace avoids fake POCs and pushes toward real success criteria on real customer data.

OMNI needs this for every serious agent/workflow:

What is the expected output?
What accuracy is required?
What is acceptable failure?
What must escalate?
What is the baseline human process?
What is the measurable improvement?
What is the rollback path?
What is the audit record?

Without this, OMNI will drift into demo theater.

9. Long-term RL needs a modeled world and gradable workflows.

Pace’s long-term view is that if agents run end-to-end workflows with expected outputs and measurable accuracy, each workflow can become a reinforcement-learning environment.

This connects strongly to the Cursor/Fireworks video.

OMNI should not jump immediately to RL, but it should design workflows so that future learning is possible:

trace every agent step,
preserve input/output,
record expected answer,
record human correction,
classify failure modes,
link outcomes,
keep procedure version,
know which tools were used.

Doctrine line:

Do not train today necessarily; structure the workflow so learning becomes possible tomorrow.

Thesis §C — Governed Capability Exchange: major. Agents need tools, writebacks, web agents, system integrations, authority gates, and explicit action boundaries.

What not to import blindly

Do not copy “no human in loop” into clinical care.

Do not assume insurance BPO accuracy targets map directly to medical safety.

Do not let agents write back into systems without explicit writeback authority.

Do not build a generic workflow DAG product if the real problem requires process-context-aware agents.

Do not let forward-deployed work become permanent custom consulting without productization.

Do-not-miss lesson

The best AI workflows are not demos. They are production processes with SOPs, evals, expected outputs, trust, and measurable improvement.

OMNI-specific:
