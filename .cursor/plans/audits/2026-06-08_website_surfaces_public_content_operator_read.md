knox to me - Yeah, this is not random. This is actually a surface ownership question, and it matters for the federation/operator model.

My answer:

The practice should not be “coding” its website. OMNI should own the website system. The federation/operator should own the business content, approvals, local positioning, service availability, offers, staff bios, hours, photos, and compliance-sensitive claims inside controlled fields/workflows.

So not “OMNI corporate manually changes every doctor’s website forever,” and not “every practice gets raw code access.”

The right model is probably:

OMNI-managed web surface + operator-configurable content + governed publish workflow.

The website is a surface, not a random marketing asset

For a medspa / derm clinic / concierge care practice, the website is not just a brochure. It becomes part of the OMNI operating system:

lead capture,
service discovery,
booking entry,
care readiness,
pre/post instructions,
patient education,
provider/staff presentation,
offers/memberships,
local SEO,
reviews/social proof,
intake routing,
compliance-sensitive claims,
consent/eligibility funneling.

So it should sit in OMNI as a surface/projection, not as a one-off Wix/Squarespace thing.

Who owns what?
OMNI owns the web platform

OMNI owns:

page templates,
design system,
components,
booking widgets,
form logic,
SEO structure,
analytics,
performance,
accessibility,
compliance guardrails,
security,
publishing workflow,
integrations,
uptime,
testing,
deployment.

This is “corporate/system” ownership.

The federation/operator owns local truth

The practice owns or controls:

business name,
locations,
hours,
phone/text/email,
providers,
services offered,
pricing visibility rules,
local photos,
bio content,
brand flavor within allowed range,
specials/offers if allowed,
local FAQs,
before/after gallery approval,
policies,
insurance/payment notes,
local regulatory disclaimers,
who can approve changes.

This is operator/local ownership.

OMNI gates what can be published

Some content should require review or constraints:

medical claims,
weight-loss claims,
peptide/Rx claims,
before/after language,
pricing/financing claims,
guarantees,
contraindication language,
prescription/service eligibility,
patient education,
provider credentials,
regulated advertising.

So the operator can edit/request, but OMNI governs publication.

Should the federation have user access?

Yes — but not raw code access.

They should have a controlled Website / Growth / Local Presence surface inside OMNI.

Something like:

“Manage Public Presence”

Where they can update:

homepage hero text from approved variants,
service pages enabled/disabled,
provider bios,
hours,
location info,
photos,
FAQs,
offers,
event pages,
announcement banners,
testimonials/reviews,
local SEO snippets,
landing pages.

But this should be field/component-based, not “edit the website code.”

What about customization for each doctor?

That should be handled by configuration + controlled content blocks, not bespoke coding every time.

Example:

A derm doctor wants a page emphasizing acne, lasers, Mohs referral coordination, cosmetics, or GLP-1. OMNI should allow:

selecting a page template,
choosing service-line emphasis,
enabling capability nodes/services,
adjusting local copy,
adding doctor bio/voice,
attaching approved education blocks,
localizing CTA,
routing forms to the correct queue,
previewing before publish.

The operator gets customization. OMNI keeps structure.

How maintenance works

Maintenance should split into three tiers:

1. Safe self-serve edits

Operator can publish or request publish for low-risk fields:

hours,
phone,
photos,
staff bio draft,
simple announcement,
local FAQ,
location details.
2. Guarded edits requiring approval

Operator can draft, OMNI/admin/approved role reviews:

medical claims,
service descriptions,
pricing language,
Rx/weight-loss content,
before/after gallery,
legal disclaimers,
promotions involving clinical outcomes.
3. OMNI-system changes

Only OMNI updates:

templates,
core components,
booking logic,
service schema,
analytics,
SEO framework,
compliance rules,
A/B testing engine,
page performance,
code/deploys.
This becomes a product feature

The product primitive might be something like:

Public Presence Surface
or
Operator Web Presence

Not sure on final name, but conceptually:

OMNI gives each operator/federation a governed, configurable public web presence that is directly connected to the operating substrate.

That means website content is not detached from OMNI truth.

If a service is not available at that location, the site should not offer it.

If a provider is not credentialed for a service, the page should not route to them.

If an offer is expired, it should disappear.

If a regulation changes, content should be flagged.

If a capability node is down/unavailable, booking should adapt.

That is the difference between a website and an OMNI surface.

Is it backdoor coding from OMNI corporate?

At first, probably yes more than we’d like.

Early wedge:

OMNI helps build/configure the site.
Internal team makes most structural changes.
Practice gets limited content-change access.
Publishing is manual/gated.

Later:

practice self-serves more.
AI drafts pages/offers/FAQs.
OMNI validates against policy/catalog/capability.
admin approves.
system publishes.

Eventually:

“Doctor wants a new acne scar landing page” becomes an OMNI request, not a developer task.

CNS/agent flow:

operator requests page,
AI drafts from approved content blocks,
pulls actual service/provider/capability data,
checks claims/policy,
previews,
human approves,
deploys,
monitors conversion/SEO/errors.

This touches:

D3 Scheduling — booking/routing.

UX/surfaces — operator admin and public web presence.
Keeper

OMNI owns the website system. The operator owns local business content within governed rails. Public websites are configurable OMNI surfaces, not detached marketing sites and not raw-code sandboxes.

And for the federation model:

A federation should be able to manage its public presence, but only through controlled fields, approved content blocks, governed publishing, and capability-aware routing.

That is the right answer.
