## Invariants (35 candidates)

### Catalog primitives

1. **Service ↔ Pricing Option many-to-many via assignment join (binding).** A service may be sellable under multiple pricing options (cash-pay $250 / membership-included / package-credit / promo-discounted / ClassPass $0). A pricing option may apply to multiple services. The join row (`service_pricing_option_assignment`) carries: `service_id` FK, `pricing_option_id` FK, `is_active` BOOLEAN, `priority` per DL-17 inv 3 redemption order, `valid_from` + `valid_to` (temporal validity per DL-16 inv 18), `disassociated_at` NULL (soft-delete distinct from `is_active=false` — disassociation preserves historical bookings + entitlement redemption audit; deactivation hides from sale UI but keeps assignment). REJECTED: nested pricing-option-arrays inside service rows; service-as-pricing-option-discriminator. Cross-link Layer 2 D.1.

2. **Pricing Option 4-type discriminator + per-type substrate.** `pricing_option.pricing_option_type` ENUM (4 values, binding): `single_session` (1 redemption; e.g., one Botox visit) / `multiple_sessions` (N redemptions per `redemption_count`; e.g., 6-pack of facials) / `unlimited_period` (unlimited redemptions within `validity_period`; e.g., unlimited yoga month) / `autopay_contract` (recurring billing per `recurrence_rule`; cross-link inv 11 Contract substrate). Each type has type-specific sub-fields (`pricing_option_single_session` / `_multiple_sessions` / `_unlimited_period` — `autopay_contract` rides Contract substrate inv 11). Mindbody (Layer 2 + Batch 13 evidence) admits exactly these 4 types; expansion requires explicit DL-17 amendment, not config flag.

3. **Entitlement Activation Strategy 3-enum (binding).** When a patient purchases a pricing option, the resulting `entitlement` row (1-to-N from pricing_option purchase per redemption count) has `activation_strategy` ENUM: `on_sale_date` (activated immediately at sale; clock starts at purchase) / `on_first_visit_after_purchase` (activated when first redemption occurs; clock starts at first visit; common for multi-session packs) / `on_custom_date` (activated on a specific future date per `custom_activation_date`; e.g., gift-card-style pre-purchase for future use). Strategy is declared at sale time, not at purchase model time — same pricing option may be sold with different strategies per sale event (rare but allowed; audited per DL-16 inv 30).

4. **Entitlement Redemption Priority 3-enum (binding) + deterministic redemption order.** When multiple entitlements are valid for the same service at booking time, the entitlement with `redemption_priority` = `high` redeems first; ties broken by `valid_to` ascending (use-it-or-lose-it first); further ties broken by `purchased_at` ascending (FIFO). Priority is declared at the pricing-option level (`pricing_option.default_redemption_priority`); per-entitlement override allowed at sale time (`entitlement.redemption_priority` overrides default; audited). REJECTED: AI deciding redemption order at runtime — order is deterministic substrate decision per DL-14 inv 18-21.

5. **Quantity Strategy enum on Pricing Option (5 values, binding).** USER FEEDBACK GAP #2 ANCHOR. `pricing_option.quantity_strategy` ENUM: `fixed_quantity` (Botox 20-unit fixed pack; quantity=20 always) / `per_unit_quantity` (variable-quantity at sale time; staff enters quantity at checkout; e.g., Botox $14/unit × N units; **eliminates Mindbody's 7-tier per-quantity workaround**) / `package_count` (N sessions per inv 2 multiple_sessions; quantity=session count) / `unlimited_period` (no quantity semantics; inv 2 unlimited_period) / `subscription_recurring` (quantity=billing periods; inv 2 autopay_contract). Per-unit quantity strategy carries `default_unit_price` + `min_quantity` + `max_quantity` + `quantity_unit` ENUM(units / syringes / vials / sessions). Build Contract anchor §3.5 inv 5 + Layer 2 D.11.

### Sale + line + payment primitives

6. **Sale (commerce order) parent + Sale Line 1-to-N child (binding).** Every commerce transaction emits one `commerce_order` row (parent) + 1-to-N `commerce_order_line` rows (children) atomically. The parent carries: `id`, `tenant_id` (brand / site / location per DL-10 + DL-16 inv 8), `patient_id` FK + `patient_relationship_id` FK (per DL-10 + primitive #19), `staff_id` FK (staff who rang sale), `created_at`, `closed_at` (atomic state transition per inv 17 closeout), `status` ENUM (per inv 17), `subtotal_amount`, `tax_amount`, `discount_amount`, `tip_amount`, `total_amount`, `payment_state` ENUM (per inv 14). Each line carries `commerce_order_line.line_kind` discriminator ENUM: `service` / `product` / `pricing_option_sale` / `gift_card_sale` / `contract_enrollment` / `package_sale` / `tip_line` / `treatment_deposit` / `cancellation_fee` / `account_credit_adjustment` / `tax_adjustment` (per inv 16 tax). Cross-link Layer 2 D.16.

7. **Price-line ≤ Subtotal invariant (binding).** Per Layer 2 D.20 + mindbody_19 Step 06 data-corruption case ($196,365 line vs $159 subtotal): every per-line amount MUST satisfy `0 ≤ line.amount ≤ commerce_order.subtotal_amount`. Substrate-level CHECK constraint (NOT app-layer only). Sum of all line amounts MUST equal subtotal exactly (no rounding drift). REJECTED: per-line amount stored independently of sum-of-lines = subtotal (the Mindbody bug pattern).

8. **Sale uniqueness within tenant + 4-tuple identity.** `(tenant_id, patient_id, opened_at, staff_id)` SHOULD identify a sale uniquely under normal operation; substrate enforces `tenant_id + commerce_order.id` UUID uniqueness only (allows back-to-back sales for same patient by same staff). Mindbody (Layer 2 D.12 receipt evidence) does NOT enforce sale-level dedup; OMNI substrate inv 8 explicitly permits multiple same-second sales per patient + staff (e.g., separate Botox + retail product transactions for one patient visit).

9. **Refund destination defaults to original payment method (binding).** Per Build Contract §3.7 patch 3. A refund created against a sale: (a) emits new `commerce_order_line` with `line_kind = refund` linked to original line via `refunded_from_line_id` FK; (b) `refund.refund_method` ENUM defaults to original payment method (`commerce_order_payment.payment_method_id`); (c) override allowed but audited per DL-16 inv 30 decision record; (d) `refund.destination` ENUM (`original_method` / `account_credit` / `gift_card_balance` / `cash_in_drawer` / `manual`); (e) substrate REJECTS refund amount > unrefunded line amount (no negative or over-refund). Cross-link DL-15 inv 6 compensation discipline.

10. **Void vs refund vs account_credit vs adjustment — 4 distinct primitives (per Build Contract §3.7 patch 3).** **Void** = pre-settlement cancellation of a sale or line (reverses the transaction; payment processor void call; `commerce_order.status = voided` + line.line_state=`voided`; no settlement occurred). **Refund** = post-settlement reversal (settled payment is reversed via processor refund call; per inv 9). **Account_credit** = `account_credit_ledger` row crediting patient balance; consumable on future sales. **Commerce_order_adjustment** = staff-initiated correction (e.g., comp a line after the fact; promote a discount that wasn't applied at sale); separate primitive with explicit audit trail; REJECTED treating adjustments as silent updates to the original sale row (original is immutable; adjustment is an additional row). All 4 require staff capability per DL-14 inv 8 + §1J.9 high-liability mutation gate.

11. **Contract / Autopay substrate with lazy template-expansion (binding).** Per Layer 2 D.17 (24-month autopay 11 synthetic future rows) — autopay schedules are NOT pre-materialized into substrate rows. The `contract` row carries: `recurrence_rule` per RFC 5545 RRULE (e.g., `FREQ=MONTHLY;COUNT=24` or `FREQ=MONTHLY;UNTIL=...`), `start_date`, `next_charge_date`, `charge_amount`, `status` ENUM (`active` / `paused` / `cancelled` / `completed` / `failed_payment_grace` / `terminated_early`). Scheduler generates virtual charge occurrences at runtime; materializes `commerce_order` rows only on actual charge attempts. **Force-run-now + edit-before-run pattern** per Layer 2 D.18: substrate allows modifying `next_charge_date` / `charge_amount` for upcoming runs without rewriting historical charges; idempotency contract per DL-16 inv 11 protects against duplicate charge emission.

12. **Package mixed-type bundle (shares Contract substrate or separate?).** OPEN sub-question (Q-DL17-1) — Mindbody (Layer 2 D + Batch 12 evidence) packages are mixed-type bundles (e.g., "3 facials + 1 Botox + $50 gift card" sold as one SKU). Two architectural options:

    - **Option B**: Separate `package` substrate distinct from contract; package_id parent + package_line 1-to-N child; entitlement generation at sale time
